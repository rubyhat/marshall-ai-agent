# Frame the Reference Question and Scope

Define why the reference is being studied before collecting evidence.

## Identify the decision

Capture:

- the target decision, hypothesis, or uncertainty;
- the intended consumer of the result;
- the target product, audience, role, market, and maturity;
- the external product, URL, artifact, or product set;
- one primary domain: UI/UX, product mechanics, onboarding, pricing presentation, positioning, or marketing evidence;
- required currentness;
- whether the result is chat-only or explicitly requested as a durable reference.

A request such as “analyze this competitor” is not yet a useful boundary. Derive or ask which journey, surface, mechanic, message, or decision matters.

## Choose the lowest sufficient mode

- Use `quick scan` for one answer that does not need a durable pack.
- Use `flow level` for a bounded journey spanning multiple surfaces.
- Use `surface level` for one coherent page, screen, step, modal, drawer, or region.
- Use `focused follow-up` for one named dimension after prior context exists.
- Use `cross-reference comparison` for one common question across multiple products.

Do not force a screen inventory or project pack for a quick scan.

## Bound the analysis

State:

- included entry and exit points;
- actors and product variants;
- desktop, mobile, locale, geography, auth, plan, or lifecycle variants that matter;
- explicit non-goals;
- maximum product or surface set;
- evidence limitations already known.

When flow-level work identifies deep-dive candidates, stop for selection unless the original request named them.

## Ask only blocking questions

Ask when the answer changes the mode, source set, target adaptation criteria, access authority, persistence, or which products are comparable. Use the configured decision-question format. Do not ask the user to choose details that can be resolved from direct evidence.
